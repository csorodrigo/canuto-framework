## Runtime Contract

### Provider and role

- Claude runtime: Claude Opus remains Maestro.
- Direct Codex runtime: Codex becomes Maestro for this session.
- Preferred launcher: `bash .agents/tools/codex-maestro.sh`
- Equivalent CLI: `codex --profile maestro`
- The `maestro` profile defaults to `o1-pro` when the account supports it and does not redefine `coder`, `reviewer`, `architect`, or `fast`.

### Memory resolution order

When loading or saving session state, use this order:

1. `~/.canuto/vault/projects/canuto-framework-v1/`
2. `.agents/vault/`
3. `.agents/memory/`
4. `.agents/.cache/pending-sync/`

If only legacy `.agents/memory/` exists, keep reading and writing the minimum compatible state there.
If no writable vault exists, queue sync payloads in `.agents/.cache/pending-sync/` and later run `bash .agents/tools/vault-sync.sh`.

### Delegation and review

- Keep the standard Maestro contract from `.agents/personas/maestro.md`.
- Use the co-review infrastructure when MCPs are available.
- `plan-review.sh` remains the legacy-compatible hook bridge for `ExitPlanMode`.
- If MCPs or Codex review infrastructure are unavailable, degrade gracefully and continue without switching runtime automatically.

### Session resume

- Claude and Codex both resume from the same memory order above.
- After offline work, sync queued entries before relying on vault-only views.
