Setup rapido

1. Instalar ou atualizar

O fluxo foi desenhado para nao exigir configuracao manual depois que o projeto recebe o framework.

01
Projeto novo

Bootstrap inicial

Use o instalador remoto quando o projeto ainda nao tem o Canuto versionado localmente.

cd /caminho/do/projeto
curl -fsSL https://raw.githubusercontent.com/csorodrigo/canuto-framework/main/install.sh | bash
02
Projeto que ja usa Canuto

Update padrao

Sempre via curl — puxa o instalador mais recente do GitHub e aplica o update. Nao use o install.sh local para update, ele pode estar desatualizado.

cd /caminho/do/projeto
curl -fsSL https://raw.githubusercontent.com/csorodrigo/canuto-framework/main/install.sh | bash -s -- --update
03
Se algo saiu do eixo

Repair e doctor

--repair reidrata o runtime. --doctor repara, valida e garante um bootstrap resumivel com .agents/tmp/context-package.md e envelope persistido no vault. Ambos sempre via curl.

Fluxo do framework

2. O que acontece depois que esta instalado

O objetivo e deixar a maior parte do orquestrador operando sozinho, mas com pontos claros de intervencao manual.

Fluxo padrao de entrega

XS: Maestro -> Coder -> Reviewer S: Maestro -> Architect -> Coder -> Reviewer M/L: Maestro -> Architect -> Coder -> Tester -> Reviewer Investigation: Maestro -> Debugger -> Coder -> Tester -> Reviewer
Runtime Claude ↔ Codex

Quem vira Maestro e como o handoff persiste

O maestro agora depende do runtime ativo. Em sessao Claude, Opus continua orquestrando. Em sessao iniciada diretamente no Codex, o Codex assume como Maestro via profile maestro. Os handoffs usam o mesmo envelope persistido no vault.

Claude executa diretamente
  • Sessao Claude — Claude Opus continua como Maestro sem mudar o contrato legado.
  • Tasks XS e S — Claude implementa sem spawn. Overhead de MCP nao justificado.
  • Architect, Tester, Debugger, Reviewer — seguem disponiveis no fluxo Claude-first.
  • Plano e briefing — entrevista, sizing, routing, contexto.
  • Quick fixes e docs — Claude edita diretamente.
Codex direto via CLI
  • Runtime direto — bash .agents/tools/codex-maestro.sh sobe o Codex como Maestro com profile maestro (alvo gpt-5.5 com reasoning: xhigh).
  • Tasks M e L — Architect gera context-package.md, chama codex exec --profile coder.
  • Tasks paralelas — multiplas chamadas codex exec --profile coder com context package por agente.
  • Pre-commit gate — codex-pretool-guard.sh dispara o reviewer path do Codex em todo git commit e explicita quando entra em fallback.
  • Plan review — ao sair do modo de plano, plan-review.sh chama o reviewer path do Codex e registra o backend real usado.
  • Retomada — o envelope com task_id, goal, constraints, done_definition e artefatos de review fica persistido em handoffs/.

Fluxo M/L em detalhe

Claude session = Opus continua como Maestro Codex direto = profile maestro (gpt-5.5, xhigh) context-package.md + handoff envelope persistido codex-pretool-guard intercepta todo git commit automaticamente

Personas em uma frase

Maestroorquestra sessao, briefing, sizing e handoffs
Architectentrevista e gera plano executavel
Coderimplementa e cobre o happy path
Testerbate nos cantos e prova o comportamento
Revieweraprova ou pede mudancas

Quando o Contextualizer entra

O Contextualizer nao fica no happy path de toda task. Ele entra quando falta contexto, quando os arquivos de contexto ficaram stale ou quando o usuario pede indexacao profunda do repo.

Fluxo: Maestro -> Contextualizer -> aprovacao do usuario -> salvar contexto
  • Bootstrap de projeto sem .context.md nem docs/FEATURE-MAP.md.
  • Atualizacao de contexto depois de mudancas relevantes de estrutura ou fluxo.
  • Pipeline Evaluate Repo para gerar indice mais profundo do codigo.
Automacao vs comando manual

3. O que funciona passivamente e o que voce precisa pedir

Esse e o ponto principal para usar o framework sem atrito.

Funciona passivamente

Roda sozinho depois da instalacao

  • Briefing inicial do Maestro ao abrir a sessao.
  • Classificacao de task e escolha do fluxo entre personas.
  • Carregamento de memoria, pending tasks e instincts no inicio.
  • plan-review.sh ao sair do modo de plano.
  • codex-pretool-guard.sh em git commit e delegacoes Codex.
  • session-save.sh no evento Stop.
  • pre-compact-save.sh antes de compactacao.
  • Disponibilizacao de profiles e MCPs depois de install.sh.
Precisa ser explicito

Voce precisa dizer ou rodar

  • curl ... | bash -s -- --update para atualizar projetos existentes (sempre via curl, nunca local).
  • curl ... | bash -s -- --repair ou --doctor para consertar e validar.
  • curl ... | bash -s -- --test para validar a integracao do projeto consumidor.
  • health check para pedir diagnostico pelo Maestro.
  • Flags como set FAST_MODE, set STRICT_MODE, skip tests.
  • Slash commands como /qa, /office-hours, /review.
  • Pedidos explicitos de skill, por exemplo use a skill research.
Referencia completa

4. Todos os comandos e frases do framework

Tudo que voce pode dizer ou rodar. Nenhum setup adicional necessario apos o install.

Terminal — Setup e manutencao

Todos os comandos de install/update/repair sempre via curl. Nunca use bash install.sh local para atualizar.

CANUTO="https://raw.githubusercontent.com/csorodrigo/canuto-framework/main/install.sh"

# Instalar em projeto novo (nao tem o framework ainda)
curl -fsSL $CANUTO | bash

# Atualizar projeto que ja usa Canuto
curl -fsSL $CANUTO | bash -s -- --update

# Check rapido de integridade de arquivos e versoes
curl -fsSL $CANUTO | bash -s -- --check

# Smoke test do projeto consumidor (HEALTHY / DEGRADED / BROKEN)
curl -fsSL $CANUTO | bash -s -- --test

# Reidratar runtime: hooks, MCPs, profiles Codex, context bootstrap
curl -fsSL $CANUTO | bash -s -- --repair

# Repair + validacao completa em uma so passada
curl -fsSL $CANUTO | bash -s -- --doctor

# Abrir runtime direto do Codex como Maestro
bash .agents/tools/codex-maestro.sh

# Sincronizar handoffs/contextos que ficaram offline
bash .agents/tools/vault-sync.sh

# Migracao de projeto existente para versao nova do framework
curl -fsSL $CANUTO | bash -s -- --migrate

# Health check do Codex (MCPs, profiles, telemetria)
bash .agents/tools/codex-health-check.sh

# Smoke test especifico do projeto consumidor
bash .agents/tools/canuto-consumer-smoke.sh

# Suite interna do framework (apenas para dev do canuto em si)
bash test-framework.sh

# Instalar hooks e mesclar settings.json localmente
bash .agents/hooks/install.sh

# Abrir este tutorial
open docs/TUTORIAL-VISUAL.html

Frases naturais que o Maestro entende

  • continue / retoma — retoma pending tasks como foco.
  • quick fix / so isso — fluxo estreito, sem Architect.
  • health check — diagnostico completo do framework.
  • set FAST_MODE — reduz rigor, pula Tester em XS.
  • set STRICT_MODE — validacoes maximas, co-review forcado.
  • skip tests — pula o Tester para essa task.
  • use a skill X — ativa skill especifica pelo nome.
  • brainstorm X com codex — dispara /co-brainstorm.
  • segunda opiniao no plano — dispara /co-validate.
  • implementa em paralelo — dispara /parallel-impl.

Interpretacao do resultado

  • HEALTHY — instalacao e runtime coerentes.
  • DEGRADED — framework roda, setup incompleto ou warning.
  • BROKEN — falha real no runtime que precisa de reparo.
  • COMMIT — pre-commit gate aprovou o diff.
  • HOLD — pre-commit gate bloqueou; ler .agents/tmp/codex/latest-pre-commit-review.md.
  • LGTM — plan review aprovado pelo Codex reviewer.
  • CONCERNS — plan review com ressalvas; resolver antes de codar.
check = integridade basica test = smoke do consumidor doctor = repair + validacao --json = saida estruturada para CI

lazy-opus-review

codex-session-writer

verification-gates

Hooks ativos

6. Onde o framework entra sem voce perceber

Esses sao os pontos do runtime que conectam Claude, Codex e o projeto consumidor.

Mapa dos hooks

  • codex-pretool-guard.sh -> intercepta git commit, comprime diff, roda gate e registra telemetria.
  • plan-review.sh -> roda review de plano quando o modo de plano termina.
  • session-save.sh -> snapshot no Stop.
  • pre-compact-save.sh -> persiste estado antes da compactacao.
  • session-load.sh -> pode ser chamado manualmente para reidratar o contexto da sessao.

O que o install/update ja prepara

  • Perfis do Codex em ~/.codex/config.toml.
  • MCPs nativos para Codex e integracao com o vault.
  • Hooks mesclados em ~/.claude/settings.json sem duplicar entradas.
  • Bootstrap de .context.md, docs/FEATURE-MAP.md e digest inicial quando faltarem.
  • Scripts de health check e smoke test disponiveis no projeto.
